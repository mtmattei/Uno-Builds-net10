Summary · what worked

What worked.

Four findings the seven runs put real evidence behind.

  1. A clean LLM-generated DESIGN.md beat every other one-shot input.
    test-3 was the cleanest run on every measured axis — 5/5 builds first-try, 0 manual corrections, 20/20 pages reachable, 0 anti-patterns shipped. A−, 85/100.
  2. An iter-1 walk-through caught what one-shot would have shipped silently.
    test-7's first iteration found empty Region.Navigator regions and a silent TimeSpan deserialization failure. Both compile clean. Both render empty. Two root-cause fixes in ~4 minutes.
  3. Skill discipline at session start dropped fix-passes 23 → 2.
    test-6's re-run with proper rules-init + Skill tool calls produced the biggest delta in the experiment. Same blind PRD, same MD3-default fidelity — 21 fewer fix passes. Discipline state dominates the FP curve.
  4. A working 20-page Uno app ships even with zero visual input.
    The negative control held. test-6 produced functional structure end-to-end with only a PRD — visual fidelity collapsed predictably to MD3 defaults. Visual input is the load-bearing variable for brand fidelity, not for functional structure.
Summary · what didn't

What didn't.

Five things the runs proved are not as good as their pitch.

  1. Figma MCP at View-seat is structurally insufficient.
    Rate-limited after ~5 calls in test-2 (4 of ~30 frames retrieved). Rate-limited on the very first call in test-5 (0 frames). For a 20-page app, this is a methodology-level blocker, not a fidelity-level one.
  2. The Figma + screenshots hybrid collapsed at minute 0.
    test-5 fell back to screenshots-only on the first Figma call, then lost the screenshot validation pass to a mid-session uno-app MCP disconnect. Pass-bar not cleared. The expected "hybrid > pixels-only" delta did not materialize.
  3. The iterative diff loop has a fidelity ceiling.
    test-7 plateaued at ~73% avg in iter-2. Iter-3 lifted it to ~76% — but only by replacing non-rendering primitives with simpler fallbacks, not by the diff mechanism closing fidelity gaps. Budget the loop for structural fixes, not fidelity convergence.
  4. uno-app MCP fragility took out 4 of 7 runs.
    Mid-session disconnects (test-1, test-5), at-session-start failure (test-6), deferred-schema friction (test-3). The single biggest delivery risk in the experiment, capping criterion-3 measurement on three runs.
  5. More spec didn't beat cleaner spec.
    test-4's 1,749-line custom visual-breakdown DESIGN.md gave the best implementation-skill discipline of any run — and shipped a deprecated Pivot pattern that crashed Windows-XamlCompiler silently. Spec quality matters more than spec volume.
Summary · what we learned

What we learned.

Five cross-cutting findings the matrix leaves behind for the next study.

  1. Visual-input modality changes which dimension fails, not whether a run passes.
    Screenshots → deep nav fails. DESIGN.md → builds clean, criterion 3 needs out-of-session validation. Blind PRD → visual collapses to framework defaults but functional structure holds.
  2. Every methodology drops MVUX, Auth, Localization, and the Toolkit composites.
    7 of 7 ran on MVVM despite upstream MVUX. utu:AutoLayout (30+ uses upstream) → 0 uses. Same for uer:FeedView, uen:Region.Attached, uen:Navigation.Request. Invisible to every methodology unless explicitly named.
  3. Discipline state dominates the FP curve more than input modality.
    Same blind PRD, 23 FPs → 2 FPs after proper rules-init. The methodology controls fix-pass volume more than what kind of visual input the agent sees. This is the load-bearing finding from the re-runs.
  4. "First-try build success" is a brittle proxy for run quality.
    test-1's original 5/5-first-try claim was a methodology artifact. The discipline-clean re-run produced 0/5 first-try because FP #1 was always real. Fix-pass volume after rules-init discriminates discipline state more cleanly.
  5. The iterative loop's load-bearing value is structural debugging, not fidelity polish.
    Iter-1 catches what compiles clean and renders empty (regions, deserialization). Iter-2+ plateaus once gaps need infrastructure work (asset re-export, native controls). Two different jobs — measure them separately.
§00 — Methodology

The kickoff prompt was ~10 lines.

The same short prompt across every test — only the test number changed. Variation lived in the SPEC and the input set, not in the agent's instructions.

Standard prompt — verbatim used by tests 2 · 3 · 4 · 5 · 8 
Read ./SPEC.md and ../SPEC.md. Verify pre-session prep is
complete (starter-kit files in place, ChefsTestN/ scaffold
exists, reference assets copied into ChefsTestN/Assets/).
Run this test end-to-end. Log to ../results/test-N.md and
../results/test-N.log. Do not read anything in the forbidden
lists of either SPEC. Before declaring done, complete every
step in ../SPEC.md §"Pre-handoff verification" and paste
the per-page checklist into the result file.
Identical for every non-discipline run. The methodology lives in the two SPEC files the prompt points at — not in the prompt itself.
01

The prompt is methodology-agnostic.

It tells the agent where to look (./SPEC.md, ../SPEC.md), not what to do. Every test's behavioral difference comes from its inputs and SPEC, not its prompt wording.

02

Forbidden inputs are enforced by the SPEC.

The prompt's "do not read anything in the forbidden lists" line delegates to per-test SPEC sections. test-3 can't read screenshots; test-1 can't read DESIGN.md; test-6 can't read any visual input at all.

03

The discipline preamble is the only delta.

Tests 1, 6, and 7 — the runs flagged for failure mode #1 or #2 — got an extra paragraph naming both failure modes verbatim. Re-runs were the only place prompt wording mattered.

Discipline preamble — added for re-runs added to tests 1 · 6 · 7 
… pay close attention to ../SPEC.md §"Skill-usage discipline"
including the two named failure modes and the self-audit gate.
This is a re-run because the prior run hit failure mode #1
(no Skill tool calls). Do NOT repeat that, and do NOT fall
into failure mode #2 (writing SKILL-USE log lines without
matching Skill tool calls). The Skill tool call comes first,
the code comes second, the SKILL-USE log line comes third
with a tool-call-summary referencing what the skill returned.
Even with this preamble, test-7 still hit failure mode #2 — the trap is sticky. The fix in the SPEC was a self-audit gate at workflow step 10.5 cross-checking transcript invocations against logged claims.

§04 — What every run did the same

Five load-bearing patterns.

Across seven different inputs and seven different processes, these five substitutions happened every single time.

  1. MVUX → MVVM, every run
    Operator default plus the absence of MVUX-only inputs steered all seven runs to CommunityToolkit.Mvvm despite the canonical app calling UseMvux().
  2. Authentication + Localization, dropped
    Auth → demo bypass on every run. Strings/{loc}/Resources.resw for en/es/fr/pt-BR never shipped.
  3. utu:AutoLayout → Grid + StackPanel
    30+ uses on RecipeDetailsPage upstream → 0 uses across all 7 tests. Same for uer:FeedView, utu:TabBar TopTabBarStyle, uen:Region.Attached, uen:Navigation.Request. The Toolkit composite library is invisible to every methodology unless explicitly named.
  4. Real interactive components, dropped
    Mapsui.Uno.WinUI + LiveChartsCore for Map and the nutrition donut → placeholder rectangles + stacked Ellipse strokes. Across all 7.
  5. Framework drift went unflagged
    Every run targeted net10.0-* while the canonical app targets net9.0-*. Real framework drift; only test-4 surfaced it as a downstream Windows-XamlCompiler crash.

§07 — continued · the why

Why the toolkit is invisible.

Five compounding mechanisms behind the substitution. Telling the agent to "use the toolkit harder" doesn't fix any of them.

  1. Inputs don't name them.
    Every visual input format — screenshots, Stitch DESIGN.md, visual-skill DESIGN.md, PRD, Figma frames — describes what to render, not which Uno control to use. Agents fill the gap with primitives they're confident about (Grid, StackPanel, Border, ItemsRepeater) because those work on every target out of the box.
  2. Pretraining priors dominate.
    Orders of magnitude more WPF / WinUI / UWP examples online use Grid + StackPanel than Uno-specific examples using Toolkit composites. When an agent infers "vertical container with consistent spacing," its default reach is StackPanel Spacing="12", not utu:AutoLayout. The primitive pattern is statistically dominant.
  3. The uno-toolkit skill loads docs, it doesn't refactor.
    test-4 invoked uno-toolkit seven times and still shipped Grid + StackPanel for layout primitives. The skill confirms utu:TabBar exists and validates BottomTabBarStyle — but it doesn't surface "your StackPanel above should be utu:AutoLayout." Skills load knowledge; they don't refactor in-progress code.
  4. uer:FeedView is structurally MVUX-shaped.
    It expects IFeed<T> / IState<T>. All 7 runs went MVVM (operator default + absent MVUX inputs). On an ObservableCollection, FeedView loses its reactive plumbing — the equivalent MVVM pattern is ItemsRepeater + HasItems + empty branch, exactly what every run shipped. The MVUX→MVVM substitution propagates downstream into "no FeedView."
  5. uen:Region.Attached has a runtime trap.
    test-7 (FP #3/#4) and test-4 (Blocker #2) both tried the canonical IsDefault: true + Region.Navigator="Visibility" pattern, hit empty regions on Skia desktop, and pivoted to flat routing. Once that lesson lands in shared memory or docs, future runs avoid the canonical pattern preemptively. The framework's own runtime gap is making the substitution stickier across runs.

The fix isn't telling the agent to use the toolkit harder. It's seeding inputs (DESIGN.md, PRD, Figma component map) with explicit Uno control mappings — or running a follow-up "Toolkit composites" experiment that does name them in the input set. That experiment is already logged as an open question.

§09 — Cliffs

The cliffs the next test shouldn't rediscover.

Adding these as up-front checklist items removes ~5–15 minutes of fix-loop per run and unblocks failures that bit multiple runs blindly.

Tier A

Universal · bit every run that touched the path

  • Svg; not in default UnoFeatures even with SkiaRenderer
  • TimeSpan is two-encoded in fixtures — {ticks:N} + "00:10:00"
  • dotnet run returns exit 0 within seconds — looks like crash, isn't
  • Image refs that don't resolve don't error — verify pre-grep on Assets/
  • Cards in ItemsRepeater/ListView need a focusable root (Button)
  • Region.Attached + Region.Navigator="Visibility" doesn't auto-instantiate (new from t-7)
Tier B

MVUX-only · bit test-6, dodged by 1/3/4/7 going MVVM

  • KE0001 — every record with Id must be partial
  • IFeed<ImmutableList<T>> ≠ IFeed<IImmutableList<T>> — invariant
  • Feed.Select(async ...) doesn't compile — use SelectAsync
Tier C

Navigation · split by methodology

  • NavigateDataAsync has no route: param — use NavigateRouteAsync
  • ViewMap<Page, Model> silently drops data: args — use DataViewMap
  • Region-based with IsDefault: true renders empty regions on Skia desktop
